# Conformance vectors

A vector records the exact bytes the core must produce for a given command and
input and, where one is given, what a device's reply must produce. The core's
test suite runs every vector, and every spec-driven command must have at least
one.

```
vectors/<spec-id>/<command>.yaml
```

## Purpose

Specs define intended behaviour; vectors record observed behaviour. Code that
agrees with its own reading of the documentation proves nothing if the reading
is wrong. Agreement with a recorded transcript does.

Vectors also gate changes. A fix reaches every consuming product at once, so a
wire-format change that does not update its vectors fails CI before release.

## Format

```yaml
spec: shure-wireless
model: slxd                  # optional; the first model supporting the command otherwise
command: get_channel_name
input: { channel: 1 }        # command parameters; defaults apply as usual
settings: {}                 # optional device settings

# What goes on the wire — exactly one of:
expect_wire: "< GET 1 CHAN_NAME >"            # text, framing included
expect_wire_hex: "2f63682f…"                  # binary (OSC, including any TCP framing)
expect_request: { method: GET, target: "/cgi-bin/ptzctrl.cgi?ptzcmd&home" }   # HTTP
# A request to an HTTP endpoint (SPEC.md §2, Endpoints) adds its port, the
# default of any setting giving it: { method: GET, port: 9996, target: /list?path=cam1 }.
# Without `port`, the request must go to the transport's own port.
# A command sending several messages lists them: expect_wire: [ …, … ]

# Optionally, a reply to feed back and the result it must produce:
device_reply: "< REP 1 CHAN_NAME {Pulpit        } >"   # text stream
# device_reply_hex: "…"                               # a datagram
# http_reply: { status: 200, body: '{"value_name":"Playing"}' }
expect_result: { ok: { kind: value, value: "Pulpit        " } }
# or { error: { error: device_error, code: "111" } } — `message` is not compared

recorded:                    # only on vectors captured from hardware
  device: Shure SLX-D4
  firmware: "1.3.9"
  date: 2026-09-29
  by: "@someone"
```

`expect_result` uses the JSON shape every delivery returns: `{ok: <outcome>}` or
`{error: <error>}`.

`recorded` is present only for vectors captured from hardware. Without it the
vector is an expectation: it locks the wire format but does not promote a
model's verification status.

## Writing vectors

The expectation vectors are generated by `tools/make_vectors.py`. There, each
expected wire format is stated by hand from the protocol's documented syntax,
and OSC bytes come from an encoder in the script itself. Nothing in it shares
code with the core, so the test suite compares the core against an independent
statement of what the wire must carry.

Add or change a vector in the script, run it, and commit the generated files
with the change they cover. Hand-written vector files, such as recorded ones,
live alongside the generated ones; use a distinct file name, for example
`get_channel_name.recorded-slxd.yaml`, so regeneration never overwrites them.

## Rules

- A spec change altering wire format updates its vectors in the same commit.
- Only a vector with `recorded` promotes a model to `bench` or `field`.
- Include failure cases. A device's response to an out-of-range channel is as
  useful as the success case.
- Binary payloads are lowercase hex with no separators; OSC padding errors are
  not visible in other representations.

## Status

Every spec-driven command has an expectation vector. None has been recorded
from hardware, which is why every model reads `verification: none`.
